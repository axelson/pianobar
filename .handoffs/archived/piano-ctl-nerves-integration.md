# Handoff: Adapt piano_ctl to control pianobar on Nerves RPi

## Context

Pianobar is now running successfully on a Raspberry Pi 3B+ with Nerves (Elixir/OTP firmware). The next step is connecting the existing `piano_ctl` Elixir app to control this remote pianobar instance.

## Current State

### Pianobar on the Pi (working)

- **Device:** Raspberry Pi 3B+ at `192.168.1.6`, running Nerves (Elixir 1.16.3, OTP 26)
- **Binary:** `/root/pianobar/pianobar` (ARMv7 cross-compiled, dynamically linked)
- **Libraries:** `/root/pianobar/lib/` (9 minimal armv6-built .so files, 4.1MB total)
- **Config:** `/root/.config/pianobar/config` (credentials configured, working)
- **Control FIFO:** `/root/.config/pianobar/ctl` (created via `mknod`)
- **Startup command:** `LD_LIBRARY_PATH=/root/pianobar/lib /root/pianobar/pianobar > /root/pianobar/log.txt 2>&1 &`
- **Status:** Pandora login works, audio playback works (tested with "Rock" station), FIFO control works (`File.write!("/root/.config/pianobar/ctl", "n")` etc.)

### piano_ctl (existing app, not yet adapted)

- **Location:** `/Users/jason/dev/piano_ex/piano_ctl`
- **What it is:** Elixir OTP app that bridges pianobar ↔ external UIs via distributed Erlang
- **Key integration points with pianobar:**
  1. **Sending commands:** `PianoCtl.CommandRunner` writes single chars to `~/.config/pianobar/ctl`
  2. **Receiving events:** Pianobar's `eventCmd` calls a generated `command.sh` script, which uses `beam_notify` socket to notify piano_ctl
  3. **Reading event data:** `PianoCtl.PianoInputReader` reads from `~/.config/pianobar/input.pipe` (a second FIFO that the event script writes metadata into)
  4. **Initialization:** `PianoCtl.Initializer` creates the FIFOs; `PianoCtl.Notifier` generates the event command script
- **Dependencies:** `libcluster`, `beam_notify`, `typed_struct`, `pid_file`
- **Config paths (all under `~/.config/pianobar/`):**
  - `ctl` — control FIFO (commands to pianobar)
  - `input.pipe` — event data FIFO (events from pianobar)
  - `command.sh` — eventCmd script (generated by Notifier)
  - `piano_ctl_pid` — PID file

## High-Level Plan

### Core Insight

piano_ctl is already Elixir, and the target device already runs Elixir/OTP (Nerves). The natural approach is to run piano_ctl **on the Pi itself**, co-located with pianobar. This eliminates the need to bridge FIFOs over the network — piano_ctl communicates with pianobar via local FIFOs exactly as designed.

### Integration Architecture

```
[Remote UI node] ←—distributed Erlang—→ [piano_ctl on Pi] ←—FIFOs—→ [pianobar on Pi]
     (laptop)                              (Nerves app)                (native binary)
```

### What Needs to Happen

#### 1. Adapt piano_ctl paths for Nerves

piano_ctl currently assumes `~/.config/pianobar/` which resolves to the user's home. On Nerves:
- Home is `/root/`
- Config is at `/root/.config/pianobar/`
- This should already work since `$HOME` is `/root` on Nerves, but verify `PianoCtl.Config` resolves correctly

#### 2. Handle the event command (`eventCmd`)

This is the trickiest part. Pianobar's `eventCmd` forks a shell script on each event (songstart, songfinish, etc.), passing metadata via environment variables. The current piano_ctl approach:
- `PianoCtl.Notifier` generates `command.sh` that uses `beam_notify` to signal the BEAM
- The script also writes event data to `input.pipe`

On Nerves:
- `/bin/sh` exists (BusyBox) but is minimal
- `beam_notify` needs its binary/script available on the device
- The generated script must use paths and tools available in the Nerves environment
- Alternative: pipe event data directly via the FIFO without beam_notify (simpler, fewer deps)

#### 3. Create the second FIFO (`input.pipe`)

We already know `mknod` works on Nerves:
```elixir
System.cmd("mknod", ["/root/.config/pianobar/input.pipe", "p"])
```

#### 4. Process lifecycle management

pianobar needs to be started/supervised. Options:
- Start pianobar from piano_ctl using `Port.open` or `System.cmd` with appropriate env
- Or keep it as a separate background process and have piano_ctl just connect to existing FIFOs

#### 5. Include piano_ctl in the Nerves firmware

Either:
- Add `piano_ctl` as a dependency in the existing Nerves project's `mix.exs`
- Or run it as a standalone release deployed to `/root/` (messier)

The first option is cleaner — piano_ctl becomes part of the firmware.

### Key Questions for Next Session

1. **Is piano_ctl already structured as a library/dependency?** Can it be added to a Nerves project's `mix.exs` directly, or does it need refactoring?
2. **Does `beam_notify` work on Nerves?** It shells out — may need the socket approach or a simpler alternative.
3. **What Nerves project manages this Pi's firmware?** We need to find where to add piano_ctl as a dep.
4. **Should pianobar be supervised by the BEAM?** Using `Port.open` would give us crash detection and auto-restart. The `LD_LIBRARY_PATH` env var can be passed to the port.
